# Scope report triage

Remediate a workstream's current code review (report mode), or the review of a pull request tied to the workstream's delivery (PR mode), in one scope-report-triage run in that workstream: verify each finding against HEAD, give every input id one outcome, commit and push the fixes, and in PR mode answer the review through `/ace:pr-response`. Run inline, with no subagents.

Read first, after Usage's `--ws` check where Usage has one; this file states only its deltas:

- `${CLAUDE_PLUGIN_ROOT}/skills/ws-shared/workstream-conventions.md` -- this skill uses the **find-only** resolution variant.
- The ws's `index.md`, once the ws is resolved, for orientation only (the conventions' `## Workstream index`).
- The ws's `decisions.md`, once the ws is resolved, read as the conventions' `## Decision log` says.
- `${CLAUDE_PLUGIN_ROOT}/skills/detect-harness/SKILL.md` -- for the harness on the `Run:` line only.
- `${CLAUDE_PLUGIN_ROOT}/skills/agent-shared/verification-checks.md`, before the first checkpoint (T11).
- `${CLAUDE_PLUGIN_ROOT}/skills/scope-implement/SKILL.md`, sections `## Git` (report mode, T5) and `## Live verification` (T11) only.
- `${CLAUDE_PLUGIN_ROOT}/skills/scope-code-review/SKILL.md`, sections `## Settled matters`, applied by this file's `## Settled matters and the owner`, and, in PR mode, `## Subject`'s default-subject test (T4) only.
- `${CLAUDE_PLUGIN_ROOT}/skills/ws-shared/orchestration.md`, section `## Probes and external state` only, where the run makes scratch or touches shared external state (`## Record`).
- PR mode: `${CLAUDE_PLUGIN_ROOT}/skills/pr-read/SKILL.md` and `${CLAUDE_PLUGIN_ROOT}/skills/pr-response/SKILL.md`, each run by reference (T4, T13).

## Usage

- `--ws` is required: without it, say so and stop.
- Input, at most one, after `--ws`: none, for report mode on the current code review; a code review file (ws-relative, or a path), for report mode on that file; or `pr <number|URL>`, for PR mode. `pr` with no next token, or with a value that is neither a number nor a pull-request URL, prints the shape `/ace:scope-report-triage --ws <path | name | slug> [<code review file> | pr <number|URL>] [instructions]` and stops, as does a bare number or a pull-request URL as the first token without `pr`. Any other first token that names an existing file is the input; otherwise it begins the trailing text.
- An input of another kind stops the run, saying why: an envelope or a closing review goes to `/ace:scope-implement --ws {ws}`, which delivers it; an old-layout `/ace:agent-code-review` file in this ws's root goes to `/ace:scope-code-review --ws {ws} leads from {file}` -- trailing text naming that file as leads, its first token resolving as nothing, so it reads as instruction text -- whose code review this skill then triages; a code review in another ws: the caller check's stop line (the conventions' `## Resolving a ws`); a review outside every ws, an `/ace:agent-code-review` file included: this skill triages only a workstream's current code review or a pull request tied to its delivery, and no other command is named; any other file, or a second input: this skill takes only this ws's current code review or one pull request.
- Trailing text steers the run: the owner's preferences; withheld commits, pushes or posts (a withheld commit, or a withheld push, commits or none, withholds every post, T12); a backlog take-up (`## Settled matters and the owner`); a requested live pass, which authorises the use it names.
- An explicit request for this skill authorises its commits, its pushes and, in PR mode, `/ace:pr-response`'s posts, overriding a repository's default rule against committing, unless the trailing text withholds them. Where the skill was chosen by inference from a looser request -- possible only where the harness allows implicit invocation -- confirm once, before its first commit, push or GitHub post and before any triage-record write ahead of it (`## Record`), naming each effect; declined, the run restores its own edits in the checkout as T11 restores a withdrawn fix's, leaving `decisions.md`, the ws's records and every path T5's proceed left as they are, checks the branch the checkout was on out again where T6 moved it -- git refusing, it says so, naming that branch -- and stops (`Stopped:`, the conventions' `## Steps`), that effect not made.

## Step

What the conventions' `## Steps` leaves to this skill:

- Open point: once T1-T5 are behind it -- the input settled, and each question they raise answered (the pull request's tie, the base) -- and any overlap question the conventions' `## Discovery and currency` asks has been answered with proceed, before its first `workings/` write, the claim (T6). Nothing is written, checked out or fast-forwarded before the open; T4's and T5's fetches, which change no branch, index or working tree, are the one thing a stop before it may leave.
- Read-only exits, beyond the conventions' shared ones (`## Steps`): every stop in Usage; no code review, a current one still at `Decisions: pending`, a named code review that is not the current one, and nothing to triage (T3); a pull request of another repository, a fork's head, a head on the default branch, a closed or merged pull request, a head that moved again, and one with no finding (T4); a declined question, or a stop answer to a routing question, before the open (T4's tie, T5's base).
- Resume: never; every run that opens takes a new step, reading earlier triage steps as evidence (T2).
- Artefact: `{nn}-scope-report-triage.md`, a triage record, and so a delivery record; input line `Source:`; `Mode: report | pr`; status field `Status:` (`## Record`).

## The run (T1-T13)

- T1 **Arguments and workstream.** Check the arguments (Usage), then resolve `--ws` (find-only) and pass the caller check.
- T2 **Records.** Read `decisions.md` (read-first list), the current envelope and closing review, and the delivery-record set (the conventions' `## Discovery and currency`; old-layout records as `## Old-layout workstreams` reads them). Earlier triage steps, finished or not, are evidence -- the ids or comments those steps' records answer, with which reply, and the commits carrying their fixes -- re-verified at the current state before anything leans on them.
- T3 **Report-mode input.** The current code review (`## Discovery and currency`), read whole: its findings, its exceptions (`Backlog:`, `Out of scope:`, `Awaiting answer:`), its Q lines, `Source:`, `Delivered:` and `Grounded at:`. Stop, saying why and printing the next step, when the ws holds none (`/ace:scope-code-review --ws {ws}`); when the current one is still at `Decisions: pending`, its run not closed (say so, naming its step, as information: its own Close prints the next steps; with no run of it going, `/ace:scope-code-review --ws {ws}`); when a named code review is not the current one (say which is current; `/ace:scope-report-triage --ws {ws}`, which takes it); and when there is nothing to triage -- no C, R or O outside its exceptions, no I carrying `Fix:` and no open Q line (its `Next:`, where it has one).
- T4 **PR-mode input**, in this order, each read-only but the fetch:
  - `gh pr view {number} [--repo {owner}/{repo}] --json headRefName,headRefOid,isCrossRepository,state`, with `--repo` when the PR is given as a URL. Stop, saying why, when the URL names a repository other than the checkout's (`gh repo view --json owner,name,defaultBranchRef`), when `isCrossRepository` is true (a fork's head), when `headRefName` is the repository's default branch (a push there would bypass the pull request), or when `state` is not `OPEN` (closed or merged). The head-name test: stop, saying why, when `headRefName` -- read as data from `gh pr view`'s JSON, never pasted into a command for this test -- holds a character outside `A-Z a-z 0-9 . _ / -` or begins with `-`. The name is pasted into shell commands, inside the double quotes the forms below keep, and quoting does not neutralise `$(...)` in bash or PowerShell, or backticks in bash. The test applies at every read of the name: this view, the re-view below, and T13.1's re-read.
  - Fetch the head: `git fetch origin "{headRefName}"`, which writes only its remote-tracking ref and `FETCH_HEAD`. Where `origin/{headRefName}` then differs from `headRefOid`, the head moved: view the PR and fetch again, once; still differing, say so and stop. `Source:`'s SHA is the head they agree on.
  - The tie: the fetched head ties to this ws when it passes scope-code-review's default-subject content test (`${CLAUDE_PLUGIN_ROOT}/skills/scope-code-review/SKILL.md`, `## Subject`) against the recorded delivered set as that section reads it; the branch name corroborates and never decides. Untied, or with no delivery recorded: one routing question -- stop (recommended: this run would push to that head and record it as this ws's delivery), or triage it here, the owner's tie recorded on `Source:`.
  - Read the PR by running `/ace:pr-read {pr}` (`${CLAUDE_PLUGIN_ROOT}/skills/pr-read/SKILL.md`) with comments on, never `--comments no`. A PR whose description and comment surfaces are all empty, or that yields no finding: say so and stop.
  - The current code review, if any, is settled context here, never input (`## Settled matters and the owner`).
- T5 **Base.** Settle the base, and ask each question it raises, before the open; check out or fast-forward only after it (T6). In either mode never stash, discard, reset, rebase or rewrite a change the run did not make. A dirty checkout is a routing question: stop (recommended), or proceed with every uncommitted path left out of the run's commits, the state record listing them, and each checkpoint run after its commit on that commit's tree, outside the checkout (T11); a fix that needs one waits for the owner to commit or discard that change, asked when met, and declined, its finding stays `awaiting answer`.
  - Report mode: scope-implement's `## Git`, read in place with these deltas and no others:
    - "the brief" reads "the code review", named on `Source:` (`## Record`), not on a `Brief:` line;
    - the code review's `Source:` and `Delivered:` name the delivery's branch beside the records in case 1, and its `Grounded at:` stands for the brief's;
    - "Settle the base before the pre-check" reads "before the open";
    - "Check the base out ... before the pre-check" reads "after the open (T6)", its clean-tree rule replaced by the dirty-checkout question above;
    - every branch name this mode puts in a command, `{branch}` below included, passes T4's head-name test first; one that fails stops the run, saying why;
    - a base branch other than the default branch with an upstream at `origin` is fetched before the open (`git fetch origin "{branch}"`) and its local branch compared with that upstream as PR mode compares the head branch below; a diverged one's new local branch, `{local}`, is `{branch}-triage` (`-2`, `-3` where taken), pushed to that upstream (`git push origin "{local}:{branch}"`), `Branch:`'s `{remote}` naming that target (`origin/{branch}`), a withheld push printed in the loop's `push {local}:{branch}` form (`## Close`);
    - in case 3 the base is the default branch's remote tip, fetched before the open (`git fetch origin "{default branch}"`), and T6 checks it out as case 3's new branch, so the local default branch is neither checked out, fast-forwarded nor pushed, as T4 refuses a default-branch head;
    - "push each checkpoint" reads "push once, after the last commit" (T12);
    - follow-ups go to the triage record's `Open:`;
    - a case-3 branch is named in Close, with the branch and pushed commits, as needing its pull request: branch information, no next step.
  - PR mode (scope-implement's `## Git` does not apply): the base is the PR's head branch at its remote head, its local branch compared with that head -- absent or equal: use it; behind: fast-forward only; ahead with commits this run did not make: a routing question -- push them with the run's own, or stop; diverged: a routing question -- stop (recommended), or work on a new local branch at the remote head, `{headRefName}-triage` (`-2`, `-3` where taken), pushed to the PR's head branch (`git push origin "{headRefName}-triage:{headRefName}"`), `Branch:`'s `{remote}` naming that target (`origin/{headRefName}`), a withheld push printed in the loop's `push {local}:{branch}` form (`## Close`), `{local}` that new branch and `{branch}` the head branch, the diverged branch left as it is. With the checkout on another branch, check the head branch out; Close names the branch it was on. Commits land only on that branch.
- T6 **Open** the step (`## Step`); its state record opens with `Source:` (`## Record`) and the `Run:` line. Then check out or fast-forward the base (T5) -- git refusing, over dirty paths: say so and stop (`Stopped:`) -- and record the base, the starting commit, the branch and the branch the checkout was on.
- T7 **Collate.** Report mode: the input ids are the code review's own -- every C, R, I, O and V finding and every Q line, `[Resolved]` ones included -- in its fixed grammar, with nothing to extract or merge. PR mode: extract findings from the description and every comment surface, since any one comment may carry a finding stated nowhere else; merge duplicates, within one surface or across them, recording each merge (which items, and why they are one finding); pair each finding with its responses by `in_reply_to_id` -- a reply or summary item marked `[x]` or `[i]` is a resolution claim, evidence for already resolved, never a finding. The input ids are the inline review comments that open a thread, each later reply in a thread that carries a finding of its own rather than a resolution claim, the review bodies and the conversation comments, by comment id, a comment carrying several findings as `{comment id} item {k}`, and the description's findings as `description item {k}`.
- T8 **Settle and verify.** Hold what `## Settled matters and the owner` settles. Verify every other finding against HEAD:
  - its anchors resolve at HEAD; one the code has already fixed or obsoleted is `already resolved`, a claimed fix verified -- the cited commit exists and the change is present at HEAD -- never trusted;
  - its recommendation is checked against the contracts around it, not only the lines it cites: a fix right for its lines can over-reach onto neighbouring rules;
  - "safe to apply" describes intent, not wording ready to paste: a proposed wording is verified against its target before it is adopted;
  - a finding that names a gap without prescribing the remedy is applied minimally, as `applied with design note` disclosing the semantics the fix invented, or deferred where the design is more than minimal or the source offers a design route;
  - an elective -- an O, an I carrying `Fix:`, or a finding its source marks as needing no action -- is applied only where the fix is cheap, as `applied as elective`; where the code review carries a systemic finding that electives would feed (growth, churn, duplication), the record names that interaction beside them.
- T9 **Ask** each owner question `## Settled matters and the owner` names, before the first commit where T8 shows it, and one met while applying when it is met; every one is settled -- answered, declined, cancelled or failed -- before the push (T12). Append each entry as it is taken (`## Decisions`).
- T10 **Work order.** Print it, then proceed without a pause: the items in priority and dependency order, each naming its owner files and its anchors verified at HEAD; items sharing a surface grouped into one naming every owner file; the merges (T7); a flag on each item whose fix restructures or reorders a procedure rather than editing locally; for an item adding a marker or state to a state machine, every state-listing site to update, or an instruction to grep the state vocabulary after applying; and a closing verification line naming the mechanical checks the content needs (stale-phrase greps, cross-file marker counts, fence parity, build or test commands as applicable), derived from the content, never an assumed toolchain.
- T11 **Apply and commit.**
  - Edit in batches per owner file, each file opened once per batch -- the electives in a later batch, so their commits stay their own -- honouring the order's cross-item dependencies. Bulk identical replacements across files may be one scripted substitution with an occurrence-count check after it, superset patterns first. An insertion between paragraphs, or into an ordered first-match-wins list, anchors across both neighbours and states its match precedence.
  - After a batch's last edit, run the order's mechanical sweep, then re-read each edited file and check every new rule against its neighbours -- ordering, vocabulary, cross-references: in full by default; the anchored region (each edit and its section) only where every edit in the file is a single-line or single-clause substitution and the sweep passed. A fix that would break what a V confirms is a deviation: redesign it, or take it to the owner.
  - Checkpoint, before each commit: verification-checks.md's `cheap` tier, derived over the run's changes and run on the tree in the checkout, plus each applied finding's `Check:`, each result in the state record (the battery in that file's record grammar) before the commit. Where T5's proceed left uncommitted paths in the checkout, each checkpoint runs instead after its commit, on that commit's tree in a disposable worktree outside the checkout (`git worktree add --detach {path} {commit}`), removed afterwards per orchestration.md's `## Probes and external state`, its results in the state record before the next commit or the push; a failure there is fixed in a further commit before the push. No `full` and no `(full: no gate resolved)` suffix: the repeat code review, or a repository's CI on the push, runs the broader battery next. A `Check:` that needs a running system follows scope-implement's `## Live verification`; declined or unreachable, it stays unverified, owned by the owner. A gate that fails only on files the run did not create and may not remove is recorded with that reason, never fixed by removing them.
  - Commit the tree the checks passed on (under T5's proceed, the commit its checkpoint then checks), the run's own paths only, the remediation first, then the electives in commits of their own, so a selective revert is a `git revert`. Each commit is made with `git commit --only -- {paths}` (a new path first marked with `git add -N`), which leaves a change the owner staged staged and out of the commit; where a check compares the tree with the index, the run's paths are staged first, the owner's left out. A check that fails after a commit is fixed in a further commit. A fix that cannot be made to pass its checks is withdrawn, the run restoring only that fix's own changes in the paths it changed for it -- a committed one by a further commit -- never another grouped item's, and deferred (`## Settled matters and the owner`); a fix whose owner question, met while applying (T9), ends without an apply answer is withdrawn, its changes restored likewise, its finding taking the outcome that answer gives it (`## Settled matters and the owner`): `held`, `deferred` or `awaiting answer`. A run that changes nothing has no checkpoint.
  - Never amend, force-push, merge, bypass hooks or commit ws records, even where `.ace/` is not ignored, and make no GitHub write but T13's (the conventions' `## Workstream`).
- T12 **Push**, once every owner question is settled and the last commit's checkpoint has passed: the branch to `origin`, a fast-forward, never forced -- in PR mode to the PR's head branch -- recording the pushed SHA. A rejected push stops the run, nothing forced and nothing posted, the triage record left at `Status: partial` naming the rejection. A push the trailing text withholds leaves the commits local, and in PR mode withholds every post, commits or none (T13's posts withheld).
- T13 **PR replies** (PR mode, after the push, with nothing to push, or with the push withheld), in this order:
  1. Re-read the PR with `/ace:pr-read {pr}`, its head name passing T4's head-name test again: a name that fails stops the run here, before pr-response runs. A comment that arrived after T4's read is no input id of this run: it is listed `next round`, `[i]`, for the next PR-mode round.
  2. Record the outcome table in the triage record and print it: one row per input id (T7) -- its outcome, its marker (`## Outcomes`), the commit for an `[x]`, the `D{n}` or reason for an `[i]` -- the description and review-body items as rows of the summary. A comment an earlier `[x]` or `[i]` reply already answers, its outcome unchanged, is marked `answered by {reply id}: no new reply`: advisory only, since pr-response answers every comment.
  3. Write `Posted: pending` on the triage record, recording in the state record the time it is written.
  4. Run `/ace:pr-response {pr}` (`${CLAUDE_PLUGIN_ROOT}/skills/pr-response/SKILL.md`) with the PR explicit, even when nothing changed and every row is `[i]`: the printed table is the work its analysis reads.
  5. Read the PR back with `/ace:pr-read {pr}`: this run's posts are the summary comment and the replies the read-back finds created after T13.3's time, by pr-read's per-comment timestamps; per row, the reply or summary item this run posted, its marker and cited SHA, against the table. Each such reply on a comment no row names, and each second reply on a row's comment, is a mismatch: `{comment id}, no row -- replied`, or `{input id} -- {k} replies`.
  6. Write the final `Posted:` (`## Record`), naming each mismatch and each item left unanswered by its input id (T7) -- the reviewer's comment, the description item or the comment item, never the reply's id; a reviewer's comment no row names, by its comment id -- and each duplicate (a new reply on a comment marked answered) by comment id. Nothing more is posted to correct one.

  With posts withheld -- by the trailing text, or by a withheld commit or push (T12): run 1 and 2, write `Posted: none -- withheld`, and run no pr-response. pr-response's gate failing after the push: the commits stand, `Posted: none -- {its reason}`, `Status: partial`, and the read-back (5) is skipped, as pr-response's own order puts that gate before its posts. A GitHub call failing mid-post: the read-back lists the ids answered and those not, `Status: partial`, and the final `Posted:` takes the form led by the summary comment's URL where the read-back finds that comment, else `none -- {why}; replies {n} of {m}`, either reading `read back matching` where the posts that landed match the table, else naming their mismatches, and naming on `unanswered:` the ids not answered. Neither is retried automatically: a retry re-posts. A read-back that itself fails is not retried either: the record keeps `Posted: pending`, read as posts that may have landed, at `Status: partial -- posts not read back: {why}`.

## Outcomes

- Every input id but an I without `Fix:` and a V (listed `no action`, below) takes exactly one outcome from this closed list, with its pointer:
  - `applied` -- the commit carrying the fix;
  - `applied as elective` -- its commit;
  - `applied with design note` -- its commit and the note;
  - `deferred` -- the `D{n}` of its `Defer:` entry;
  - `rejected` -- refuting evidence, a file:line chain or a probe, so the repeat review can retire it; an elective not taken (T8): `elective, not taken: {reason}`;
  - `already resolved` -- the commit or evidence that resolved it;
  - `held` -- the accepted or open `D{n}` that holds it, else the code review's `Backlog:` or `Out of scope:` line;
  - `awaiting answer` -- the open question.
  With commits withheld, an applied form points to the paths left uncommitted. Under a followed `[deferrable]` question it adds `(follows {code review file}#Q{n})`.
- Report mode: a C, R or O outside the exceptions takes the outcome its fix earned; a `Backlog:` or `Out of scope:` finding is `held`, unless its entry's trigger has fired or the evidence shows more impact -- then verified; an `Awaiting answer:` finding, or a `Follows:` one on a `[blocking]` Q, is `awaiting answer` unless this run settles its question; a `Follows:` one on a `[deferrable]` Q takes the outcome its fix earns, `(follows {code review file}#Q{n})`. An I carrying `Fix:` takes an outcome; every other I, and every V, is listed `no action`. A Q line: answered in this run, the outcome its answer earns, as for a finding (`## Settled matters and the owner`); `[deferrable]` and followed, `applied (follows {code review file}#Q{n})`, left open with no entry; declined or unanswered, `awaiting answer`; already `[Resolved]`, or settled by an entry whose Context names it, `already resolved -- D{n}`.
- PR mode: every input id of T7.
- `deferred`, `rejected` or `held` on an unheld `[high]` C or R -- one on neither `Backlog:` nor `Out of scope:` with an accepted `D{n}` -- and `deferred` on a PR-mode input id carry an owner-answer `D{n}`.
- Markers, PR mode: `[x]` for the three applied forms and `already resolved`, each citing the commit now carrying the fix (an already-resolved one: the commit that resolved it); `[i]` for the rest.

## Settled matters and the owner

- Settled, as scope-code-review's `## Settled matters` reads them: accepted entries; the closing review's verdicts and dispositions; open `Defer:` entries, unless the revisit trigger has fired or the evidence shows more impact than the entry records, the trigger tested as that section tests it. Settled too: the code review's exceptions -- `Backlog:` and `Out of scope:` hold their findings, unless their entry's trigger has fired or the evidence shows more impact, `Awaiting answer:` waits on its question -- and its V findings, regression guards whose confirmed behaviour every fix keeps. In PR mode a comment matching a held finding or an accepted entry is `held`, its `[i]` citing the entry, unless it carries evidence against it.
- Backlog is taken up only where the trailing text asks, as an owner-answer entry superseding its `Defer:`.
- Without an owner answer, this skill changes no scope, goal, gate clause or accepted entry, and sets aside no unheld `[high]` C or R: it has no sceptic or verifier, and runs after the closing review. Each of these is an owner question, a substantive one keeping the keep-current option (the conventions' `## Questions outside the interview`): a fix that would make such a change; deferring, rejecting or ratifying an unheld `[high]` C or R, a request in the trailing text to do so included; deferring a PR-mode finding; evidence against an accepted entry; an open `[blocking]` Q of the code review; and a choice between relatively equal fixes. A `[blocking]` Q is asked with its own options and recommendation, keep current behaviour taking one of the three slots unless an option already keeps it; the others with: apply it, the answer recorded; defer it, with a revisit trigger -- to a scope run (`/ace:scope-review --ws {ws}` or `/ace:scope-envelope --ws {ws}`) where the change is the scope's; or keep current behaviour. Recommended, for the others: the fix, where the question is setting aside an unheld `[high]` C or R; keep current behaviour, where it is a change to the scope, a goal, a gate clause or an accepted entry, unless the evidence is strong; otherwise the option the evidence favours.
- An actual answer, keep current behaviour included, appends one owner-answer entry -- headed `Defer:` where it defers a finding, one per finding it defers -- and the finding's outcome follows it: the applied form, its `D{n}` beside the commit; `deferred`; or, kept as it is, `held -- D{n}`. A declined, cancelled or failed question appends nothing and leaves its finding `awaiting answer`; an unheld `[high]` one keeps the next review `not ready`.
- A `[deferrable]` Q is not asked: it is followed at its recommended option and left open -- the code review's fix-or-decline question on its unheld `[high]` findings among them, whose recommended option has those findings fixed.
- This run defers on its own say, with a direction `Defer:` entry, only an O, an I carrying `Fix:`, or a `[low]` C or R that T8's gap rule or T11's withdrawal sends there -- never an unheld `[high]` C or R, never a finding whose owner question was asked, and never a PR-mode finding; applying a PR-mode finding, rejecting it with evidence and `elective, not taken` stay its own call.

## Decisions

- Keep the ws's `decisions.md` header and follow it, an older-seeded one included: this skill never replaces a header (scope-implement's replacement is that skill's own). The run is the one writer; with no interview, it appends each entry as it is taken, pending ones before any stop.
- Source: the header's form for a decision made outside a report, naming this step's state record (`workings/{nn}-scope-report-triage/state.md`), with `owner answer`, `owner override (recommended: {option})` or `direction`. Report ids are cited `{file}#{id}`; an answer that settles a code review's Q names it in Context as `{code review file}#Q{n}`. The code review is never edited: only its writer marks its questions, and the log overrides it. Where the header states a form or rule, the header's wins; the forms here and below apply where it states none.
- Each `Defer:` entry is headed `Defer: {code review file}#{id} -- {short description}` or `Defer: {owner}/{repo}#{n} comment {id} -- {short description}`. On its own say the run appends only the `Defer:` entries `## Settled matters and the owner` allows, and supersedes, narrows or takes up no entry.

## Record

- The state record, `workings/{nn}-scope-report-triage/state.md` (the conventions' `## Steps`), current as the run progresses: after its opening lines, the base, the starting commit, the branch and the branch the checkout was on, and the uncommitted paths a proceed answer left out (T5); the work order; each question with its answer or decline, and each entry appended; before each commit (under that proceed, after it), its checkpoint's results (T11), their outputs kept beside it; each commit and pushed SHA as it is made; the outcome table; each id the read-back finds answered. Scratch goes outside the checkout; removal and shared external state: `${CLAUDE_PLUGIN_ROOT}/skills/ws-shared/orchestration.md`'s `## Probes and external state`.
- The triage record, `{nn}-scope-report-triage.md` in the ws root, is the step's artefact: written at `Status: partial` immediately before the run's first commit, push or post, or T13's first record write where that comes first, after any confirmation Usage requires, and rewritten after each commit, after the push, at T13's outcome table, at each `Posted:` write (`pending` before pr-response posts, then the final value), and at its close, so no stop leaves a commit, push or post unrecorded, and a crash at most the effect just made, which the branch, its remote or the pull request still shows (T2); a stop before then writes `Stopped:` (the conventions' `## Steps`). `Posted:`, the markers, the answered marks and `next round` are PR mode's; in `replies {n} of {m}`, `{m}` is fixed at T13.2, before any post, from the outcome table: the inline review comments its rows name, each counted once, `next round` and `answered by` rows included -- the comments pr-response answers by threaded reply -- and `{n}` those of them the read-back finds this run answered; a mismatch or an unanswered item is named by its input id (T7), a reply on a comment no row names by that comment's id (T13.6). Until T13 writes it, `Posted:` reads `none -- not yet posted`; a stop before T13.3 (a rejected push, a failed re-read) leaves `none -- {why}`, and pr-response stopping before its posts -- at its gate or an earlier step -- leaves the gate's `none -- {its reason}`, the read-back skipped. `## Merged` holds T7's merges only, never T10's surface groupings; an empty section is omitted. `Source:` names the triaged input and `Checks:` may read `none -- no change` as the conventions' header-order bullet (`## Steps`) says; its battery is the run's final result, the last checkpoint's `cheap` battery, as a triage runs no `full` tier (T11). `Commits:` reads `none -- pending` on a write before the run's first commit, and `Checks:` reads `pending` on a write before its first checkpoint (under T5's proceed, a write before the first commit). `Open:` takes the handoff's form, its items a triage's own: it delivers no stages, so it reports no drift; it tests a `Defer:`'s trigger only where the entry would hold one of its input ids, which then takes an outcome (`## Settled matters and the owner`), so it lists no such entry; and it adds its awaiting answers, unverified checks and next-round comments.

## Close

- Close is the triage record's final write, at `Status: complete`, or `partial -- {what remains}` after a stop with work left or a failure past the push; an effect the trailing text withheld is no work left: the record names it, and Close prints its route; an id awaiting answer is no work left: `Open:` lists it. Then print the triage record's path and status, the outcomes (each id not applied named, with why), the D ids appended, the files carrying electives, the checks, the branch and pushed commits or none and why, `Posted:` with every mismatch, unanswered id and duplicate, every withheld effect, the branch the checkout was on where T5 moved it, and the next steps: the conventions' `## Hand-off loop` triage edges, in that section's form, written on `Next:` as printed.
- Next steps, each that applies; this run judges which, and the effects it withheld or that failed, whose owner's actions go before the edge:
  - Report mode, commits made or withheld: the loop's report-mode edge, with the owner's action that edge gives a withheld commit or push.
  - Report mode, no commits: the loop's report-mode edge, this run judging whether the `decisions.md` entries it appended hold a finding or settle a question of the code review, as that edge defines it, whether the code review still covers the delivery, and its verdict.
  - PR mode, replies posted: the loop's PR-mode replies-posted edge, this run judging whether it pushed content.
  - PR mode, posts withheld (T13): the loop's PR-mode posts-withheld edge, this run judging which it withheld and whether it pushed content or left content for the owner's push. Not printed, as it describes that run: the re-run opens a new step and finds the pushed fixes already resolved and posts.
  - At `Status: partial`, in place of the mode's edge above: the loop's partial edge, `pr {number}` added in PR mode; after a rejected push, its clause ` -- once {cause} is cleared`, worded by the run in the loop's clause form (the conventions' `## Hand-off loop`); after pr-response's gate failed, the owner's action before that edge, `put the pushed fixes on the head of pull request {number}`; where this run pushed content, the code-review line before merge. In PR mode after a failure mid-post or a failed read-back, say, as Close text off `Next:`, that the re-run's pr-response answers every comment again, so its replies duplicate those this run posted, which its `Posted:` lists as duplicates.
